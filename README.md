# 인터랙티브 웹 워크숍

Vite + TypeScript 프로젝트입니다. 상단 메뉴에서 하트 풍선, 글자 포획, 시선 추적, 단어 피하기, 3D 인형뽑기, 키 샘플러, Lemonade, WaterTouch, Balloon, DoodleFace, 고무 인간, Shampoo, 동물의 숲을 선택합니다.

```sh
npm install
npm run dev
```

## GitHub Pages 배포

GitHub 저장소 **Settings → Pages → Build and deployment → Source**를 **GitHub Actions**로 설정합니다. 변경 사항을 `main`에 푸시하면 `.github/workflows/deploy.yml`이 의존성을 설치하고 `npm run build`로 생성한 `dist` 폴더를 배포합니다. 진행 상태는 저장소의 **Actions** 탭에서 확인합니다.

배포 주소: https://youngsun-onearth.github.io/Interactive-Web_6/

`vite.config.ts`는 빌드 시 `/Interactive-Web_6/`를 기본 경로로 사용합니다. 저장소 이름이나 배포 주소를 바꾸면 이 경로도 수정해야 합니다. 로컬 개발 경로는 `/`입니다.

저장소 루트를 그대로 배포하면 원본 `index.html`이 `/src/main.ts`를 요청해 404와 흰 화면이 발생합니다. 반드시 빌드 결과인 `dist`를 배포하세요. `dist`를 Git에 커밋할 필요는 없습니다. 서버 없이 빌드만 확인하려면 `npm run build`를 실행합니다.

## 모든 예제의 공통 촬영

화면 하단 중앙의 흰색 원형 버튼은 01–12 모든 예제에 표시됩니다. 짧게 누르면 사진을 촬영하고, 0.45초 이상 길게 누르면 동영상 촬영을 시작합니다. 다시 누르면 녹화를 종료하고 저장 미리보기를 엽니다. 촬영 중 예제를 바꾸면 같은 영상에 다음 예제도 이어서 담깁니다.

일반 예제의 DOM 화면과 3D 인형뽑기/Lemonade/WaterTouch/Balloon/DoodleFace의 캔버스 장면을 저장합니다. 촬영 버튼과 예제 선택 메뉴는 저장 결과에 포함되지 않습니다. 일반 예제는 카메라 권한 없이 촬영할 수 있고, Lemonade·WaterTouch·Balloon·DoodleFace의 실시간 카메라 배경을 사용하려면 별도로 카메라를 켭니다. 일반 DOM 예제의 영상 갱신 속도는 기기 성능과 화면 복잡도에 따라 달라집니다. 영상은 무음입니다.

구현은 `src/capture.ts`, 공통 버튼과 저장 창 스타일은 `src/capture.css`에 있습니다.

## 07 · Lemonade

`카메라 켜기`를 누르고 카메라 권한을 허용합니다.

- 왼손: 떠 있는 레몬 근처에서 주먹을 쥐면 잡힙니다. 주먹을 유지하면 레몬이 눌리며 즙이 떨어지고, 손을 펴면 놓습니다. 다 짠 레몬은 찌그러진 채 낙하하고 새 레몬으로 교체됩니다.
- 오른손: 컵의 중앙이 손바닥 중앙을 따라갑니다. 손이 사라지면 컵이 하단 중앙으로 돌아옵니다.
- 컵: 입구로 들어간 즙만큼 채워지고 얼음과 안쪽 레몬 슬라이스가 수면을 따라 올라갑니다. `새로 만들기`로 초기화합니다.
- 빨대: 컵이 가득 차면 빨대가 나타납니다. 오른손으로 컵을 들어 빨대 끝을 입가에 대면 입 위치를 인식해 빨대 속 레몬에이드가 위로 이동하고, 컵의 양도 점차 줄어듭니다. 입 위치 인식은 이 시점에만 지연 로드되어 기기 안에서 처리됩니다.
- 촬영: 짧게 눌러 사진, 0.45초 이상 길게 눌러 동영상. 녹화 중에는 빨간 테두리와 빨간 정지 사각형이 표시됩니다. 손을 떼어도 녹화는 이어지며, 다시 누르면 종료합니다.
- 저장: 미리보기의 `파일 저장`으로 다운로드합니다. 파일 공유를 지원하는 기기는 `공유 / 사진 앱에 저장`에서 시스템 저장 메뉴도 사용할 수 있습니다. 영상은 마이크 없는 무음 촬영이며, 최대 3분입니다.
- 접근성: 촬영 버튼에 포커스를 둔 상태에서 Enter 또는 Space도 짧게/길게 누를 수 있습니다.

레몬 이미지는 [`public/lemonade/README.md`](public/lemonade/README.md)를 참고해 교체합니다. 이미지 이름과 즙 양은 [`public/lemonade/config.json`](public/lemonade/config.json)에서 설정합니다.

## 08 · WaterTouch

`카메라 켜기`를 누른 뒤 양손을 펼치면 엄지부터 새끼손가락까지 열 손가락 끝이 물결을 만듭니다. 손끝을 움직이면 이동 경로에 연속적인 물살이 생기고, 물결이 퍼져 서로 간섭하면서 카메라 영상이 굴절됩니다. 손이 사라지면 새 물결은 멈추고 남은 파동은 자연스럽게 잦아듭니다. `잔잔하게` 버튼은 물결을 초기화합니다.

Lemonade와 같은 로컬 MediaPipe 모델을 사용하며, 거울처럼 좌우 반전된 카메라의 cover 크롭과 손 좌표를 일치시킵니다. 최대 192셀의 물 표면에서 파동을 계산하고 WebGL로 카메라를 굴절시킵니다. WebGL을 사용할 수 없거나 컨텍스트가 끊기면 낮은 해상도의 Canvas 굴절로 계속 동작합니다. 장면은 24–30fps, 추론은 기기 성능에 따라 약 8–10fps로 제한합니다. 예제를 떠나면 카메라·손 인식 모델·GPU 리소스를 해제합니다.

공통 촬영 버튼으로 물결이 적용된 카메라를 사진 또는 무음 영상으로 저장합니다. WaterTouch 저장 미리보기를 보는 동안에는 카메라 그리기·물결·추론을 멈추고 GPU 렌더러를 해제하며, 미리보기를 닫으면 이어서 동작합니다. 카메라만으로 물리적인 접촉 깊이를 측정하는 방식은 아니며, 화면 안에서 인식된 손끝을 물 표면의 접촉 지점으로 사용합니다.

## 09 · Balloon

`카메라 켜기`를 누르면 전면 카메라가 전체 화면에 표시되고, 크기와 색이 다른 풍선이 화면 하단 밖에서 계속 올라옵니다.

- 검지 끝이 풍선 본체에 닿으면 즉시 터지며, 같은 색의 파편이 사방으로 퍼집니다.
- 엄지와 검지를 가까이 모아 풍선 아래의 끈을 집으면 해당 풍선이 상승을 멈춥니다. 핀치 지점이 끈 끝을 따라가며, 풍선은 탄성 있는 끈에 매달린 것처럼 약간 늦게 움직입니다.
- 풍선이 입가에 닿았을 때 입을 O자로 오므리면 바람을 부는 것처럼 풍선이 카메라 쪽으로 커지며 미세하게 흔들립니다. 입 모양을 풀면 원래 자리와 크기로 돌아간 뒤 다시 떠오릅니다.
- `새 풍선`은 현재 풍선과 파편을 정리해 새 장면을 만듭니다. 저장 미리보기 중에는 카메라와 애니메이션을 잠시 멈추고, 닫으면 다시 이어집니다.

## 10 · DoodleFace

한 PC의 한 카메라 앞에 두 사람이 나란히 서서 플레이합니다. `2인 게임 시작`을 누른 뒤 왼쪽과 오른쪽 절반에서 얼굴이 각각 안정적으로 인식되면 5초 카운트다운 후 두 카메라 영역이 0.85초 동안 서로 반대편으로 미끄러져 교환되고 60초 게임이 시작됩니다. 각 플레이어는 자기 쪽 화면에 나타난 상대 얼굴을 꾸밉니다.

- 엄지와 검지 중간이 상대 화면의 펜 끝 위치가 됩니다. 얼굴 안에서 선을 시작하면 핀치를 놓을 때까지 얼굴 밖으로 나가도 같은 획이 이어지고, 얼굴 밖의 부분까지 얼굴과 함께 움직입니다.
- 각 화면 상단의 색 위에서 해당 플레이어가 핀치하면 펜 색이 바뀝니다. 마우스 클릭도 보조 입력으로 사용할 수 있습니다.
- 한 번의 MediaPipe 추론에서 얼굴 두 개와 손 두 개를 감지하고, 화면 절반을 기준으로 PLAYER 1과 PLAYER 2에 고정 배정합니다.
- 그림 좌표는 상대 얼굴 랜드마크에 고정되며, 감지 사이의 이동·크기·회전을 예측해 빠르게 따라갑니다. 네트워크 전송이 없으므로 양쪽 그림은 즉시 나타납니다.
- 60초가 지나면 작은 결과 안내가 약 2.4초 동안 나타났다가 사라집니다. 이후 약 10초 동안 서로의 결과 얼굴을 보여준 뒤 처음 선택 화면으로 돌아갑니다.

네트워크, 방 서버, WebRTC, 환경변수 설정은 사용하지 않습니다. 얼굴·손 모델과 WASM도 `public/mediapipe`에 포함되어 실행 중 외부에서 다운로드하지 않습니다.

다른 프로젝트에서 동일한 콘텐츠를 재현할 때 사용할 전체 요구사항은 [DoodleFace 단일 생성 프롬프트](docs/DOODLEFACE_SINGLE_PROMPT.md)에 정리되어 있습니다.

## 11 · 고무 인간

`카메라 켜기`를 누른 뒤 얼굴 위에서 엄지와 검지를 맞대고, 핀치를 유지한 채 손을 움직입니다. 처음 집은 얼굴 텍스처 지점이 손을 따라가고, 그 주변은 MediaPipe 얼굴 삼각 메시의 거리별 감쇠를 통해 곡선으로 늘어납니다. 두 손을 각각 얼굴 위에서 핀치하면 두 지점을 동시에 잡을 수 있습니다.

핀치를 놓으면 저감쇠 스프링이 원래 위치를 지나 살짝 튀었다가 점차 정지합니다. GPU에서 전체 얼굴 메시를 한 번에 렌더링하며, WebGL을 사용할 수 없는 환경에서는 Canvas 삼각 변환으로 동일한 인터랙션을 유지합니다. 예제를 떠나거나 페이지가 숨겨지면 카메라·추론 모델·GPU 리소스를 해제합니다.

## 12 · Shampoo

`카메라 켜기`를 누르고 얼굴과 머리 전체를 비추면 HumanSeg의 `selfie` confidence mask가 이마 라인 위 실제 머리카락 실루엣을 찾습니다. 기본 거품은 이마 라인과 HumanSeg 경계 사이의 머리 영역 전체를 조밀하게 채우며, 좌우·정수리·이마 쪽 가장자리에서 큰 기포가 경계를 조금 넘어 자연스럽게 보입니다. 각 기본 거품은 매 프레임 가까운 HumanSeg 경계의 법선과 접선 방향을 다시 계산해 경계 모양을 따라 미세하게 움직입니다. 별도의 경계선은 표시하지 않습니다. 랜드마크 기반 경계 fallback은 사용하지 않으며, 유효한 HumanSeg 결과를 얻기 전에는 기본 거품을 표시하지 않습니다. 머리 위로 솟는 기본 거품 기둥은 만들지 않습니다.

얼굴의 위치·크기·기울기를 실시간으로 추적하며, 두피 거품 전체가 감쇠된 관성과 마찰로 부드럽게 따라갑니다. 이마 쪽 하단 실루엣은 중앙과 관자놀이 양쪽에서 접선이 끊기지 않는 둥근 곡선을 사용합니다. Pinch를 하지 않아도 손바닥과 다섯 손가락 끝이 두피 거품에 닿으면 손의 속도와 접촉 방향이 전달되어, 손으로 밀거나 쓸어내는 방향으로 탄성 있게 움직입니다. 주먹을 쥐면 닿은 두피 또는 얼굴 부근에서 더 큰 여러 겹의 미세 기포 다발이 탄력 있게 피어납니다. 얼굴 내부나 얼굴 윤곽 가까이에서 Pinch를 시작하면 손을 떼기 전까지 이동 경로에 거품이 계속 생성됩니다. 시작점이 얼굴 안이었다면 손이 얼굴 밖으로 이동해도 스트로크가 유지되며, 모든 거품은 가장 가까운 얼굴 랜드마크의 상대 위치에 고정되고 `새 거품`을 누르기 전까지 절대 제거되지 않습니다. 중앙은 훨씬 많은 미세 흰 기포를 빽빽하게 겹치고 외곽으로 갈수록 기포 수와 불투명도를 함께 낮춰, 별도 외곽선 없이 자연스러운 비누거품 그라데이션을 만듭니다. `새 거품`으로 두피 거품 배치와 얼굴에 만든 거품을 초기화할 수 있습니다.

Shampoo의 손 추론은 별도 Worker에서 실행하고, HumanSeg는 손 제스처가 없는 구간에 낮은 빈도로 갱신합니다. 거품 원과 부착 거품 뭉터기는 캐시된 스프라이트로 그려 메인 스레드의 프레임 부하를 줄였으며, 얼굴 포즈는 HumanSeg 갱신 사이에도 이동·회전·확대를 즉시 반영합니다. 손 랜드마크가 잠깐 사라지면 950ms 동안 마지막 상태를 유지하고 얼굴은 760ms 동안 마지막 포즈를 유지해 순간적인 감지 누락에도 상호작용이 끊기지 않습니다. 얼굴 또는 두피 영역에서 주먹 거품 생성을 시작하면 손을 펼 때까지 360~460ms 간격으로 큰 거품 군집이 계속 생성되며, 주먹이 얼굴 밖으로 이동해도 보간된 경로를 따라 끊김 없이 이어집니다. 주먹 군집은 중심 코어 주위에 나머지 군집을 넓은 방사형으로 배치하고 각 기포 크기도 키워 얼굴 너비의 약 66%에 해당하는 큰 영역을 차지합니다. 렌더링 군집 수는 늘리지 않아 장시간 생성 부하를 억제하며, 손을 폈다가 다시 쥐거나 Pinch로 전환한 뒤에도 반복할 수 있습니다. 얼굴에 부착된 각 거품 뭉터기는 가장 가까운 개별 얼굴 랜드마크 번호와 상대 오프셋을 저장합니다. 따라서 얼굴 전체의 이동·회전·확대뿐 아니라 표정으로 해당 피부 지점이 움직일 때도 그 랜드마크를 따라갑니다.

현재 프로젝트에는 로컬 HTTPS 인증서가 생성되어 있습니다. 다른 PC에서는 최초 한 번 이 개발 PC의 mkcert 루트 인증서를 신뢰하도록 설치하고 카메라 권한을 허용해야 합니다. 인증서의 IP 주소와 실제 개발 PC의 IP가 달라지면 아래처럼 인증서를 다시 만듭니다.

```sh
mkcert -cert-file certs/localhost.pem -key-file certs/localhost-key.pem localhost 127.0.0.1 ::1 192.168.x.x
```

## 카메라와 모바일 실행

카메라는 **HTTPS 또는 localhost**에서만 사용할 수 있습니다. PC의 `http://192.168.x.x:5173` 같은 주소를 휴대폰에서 열면 카메라가 차단되므로, 휴대폰 테스트에는 HTTPS 호스팅 또는 신뢰할 수 있는 HTTPS 개발 주소를 사용하세요. 카메라 권한이 막혀 있으면 해당 사이트 권한에서 허용해야 합니다.

Android Chrome, iOS Safari와 iOS의 WebKit 기반 브라우저, macOS Safari/Chrome/Firefox, Windows Chrome/Edge/Firefox를 대상으로 구성했습니다. MediaRecorder의 지원 형식을 조회해 MP4(H.264)를 우선 선택하고, 지원되지 않으면 WebM으로 녹화합니다. 모바일 화면 회전 시 녹화 파일의 해상도는 유지되고 필요한 여백이 추가됩니다. Lemonade를 벗어나면 카메라는 꺼지지만 공통 화면 녹화는 다음 예제에서 이어집니다. 페이지가 백그라운드로 가면 녹화를 마무리하고 저장 미리보기를 표시합니다.

Instagram·카카오톡 인앱 브라우저는 앱 버전과 운영체제 권한 정책에 따라 카메라 또는 파일 저장을 차단할 수 있습니다. 이 경우 화면에 Safari/Chrome으로 열라는 안내를 표시합니다. 인앱 브라우저에서도 카메라가 허용된 환경에서는 같은 기능을 사용합니다.

MediaPipe Hand Landmarker는 최대 두 손을 인식합니다. 추론 입력과 화면을 같은 방향으로 미러링하고 cover 크롭을 동일하게 적용합니다. 손 구분이 반대로 느껴지는 카메라 환경에서는 `손 좌우 전환`을 사용할 수 있습니다. 손 인식은 조명, 손의 가림과 기기 성능에 영향을 받습니다.

모델과 WASM은 `public/mediapipe`에 포함되어 있으며 카메라를 켤 때만 지연 로드됩니다. Lemonade 손 인식은 기기 성능에 따라 약 11–15fps, 입력 영상은 512–640px로 조절하고 GPU 초기화가 실패하면 CPU로 재시도합니다. WaterTouch는 동기식 추론을 전용 Web Worker의 CPU/WASM으로 분리하고 360–480px, 약 8–10fps로 제한해 화면 입력과 애니메이션이 막히지 않게 했습니다. 물결 장면은 24–30fps를 목표로 하며 모바일·저사양 기기는 긴 변 720px, 그 외 기기는 960px 이내에서 렌더링합니다. 프레임 지연이 반복되면 자동으로 그리기 빈도를 낮춰 입력 응답과 냉각 여유를 확보합니다. 카메라 영상은 서버로 업로드하지 않습니다.

## 13 · 동물의 숲

둥근 나무와 겹겹의 잎, 풀과 꽃, 흙 절벽, 굽이치는 강과 호수가 구 전체를 덮는 3D 숲 지구본입니다. 서로 다른 지형 경로와 식생 군락을 배치하며, 같은 맵 조각을 반복해서 붙이지 않습니다. 과일나무·침엽수·꽃나무, 버섯·양치식물·쓰러진 통나무와 작은 나무 다리가 숲 사이에 놓여 있습니다.

- 마우스로 드래그하면 지구본을 회전합니다.
- 마우스 휠로 지구본을 확대·축소합니다.
- 기존 공통 촬영 버튼으로 사진과 무음 영상을 저장합니다.
- `/#animal-forest` 주소로 바로 열 수 있습니다.

구현은 `src/animal-forest.ts`, 스타일은 `src/animal-forest.css`입니다. Three.js를 지연 로드하고 나뭇잎·꽃·풀은 InstancedMesh로 그립니다. 이번 추가에서는 데스크톱 비주얼과 드래그·줌 동작을 우선 확인했으며, 전체 플랫폼 검증은 수행하지 않았습니다.


### 주민 입주

`입주하기`를 누르면 왼쪽에 카메라, 오른쪽에 이미지 선택 창이 열립니다. 이미지를 드래그하거나 선택하면 카메라가 준비된 시점부터 5초를 세고 사진을 촬영합니다. 촬영 후 카메라 화면과 업로드 창이 닫히고, 완성한 주민을 약 3.4초 동안 크게 보여준 뒤 약 2.7초에 걸쳐 지구본으로 축소해 입주시킵니다. 입주한 주민은 구면에 발을 붙인 채 걷고, 방향 전환과 잠깐 쉬기를 반복하며 물과 나무, 다른 주민을 피합니다. 여러 명을 연속해서 추가할 수 있습니다. 주민은 이 브라우저의 IndexedDB에 저장되어 새로고침하거나 브라우저를 다시 열어도 복원됩니다.

현재 구현은 **로컬 이미지 분류·실루엣 기반 절차적 모델링**입니다. 범용 생성형 이미지→3D 서비스나 사진의 보이지 않는 뒷면을 복원하는 모델은 연결되어 있지 않습니다. EfficientNet 분류와 실제 이미지 윤곽에서 귀·주둥이·머리·몸의 비율을 결정하고, 인식 가능한 동물과 사람은 큰 머리와 짧은 팔다리를 가진 미니어처로 만듭니다. 그 외 물건·미분류 형체는 배경을 분리한 실제 윤곽을 닫힌 입체 메시로 부풀립니다. 복잡한 배경, 여러 형체, 분류 모델이 학습하지 않은 캐릭터는 인식이 부정확할 수 있으므로 형체 하나가 중앙에 있는 사진 또는 투명 배경 이미지를 권장합니다.

촬영 사진은 HumanSeg 내부를 추출하고, 전신을 감지한 경우 Pose 마스크와 교차해 배경을 더 엄격하게 제외합니다. 보이는 얼굴·몸통·팔·다리 랜드마크에서 부위별 UV 텍스처를 만들고, 경계와 뒷면은 해당 사람 부위에서 얻은 색으로 자연스럽게 연결합니다. 가려지거나 화면 밖에 있는 팔다리는 보이는 몸통 질감을 사용하며 정확한 해당 부위 매핑을 보장하지 않습니다. 팔다리가 없는 윤곽형 주민은 사람 전체의 배경 제거 텍스처를 사용합니다. 인식은 별도 Worker에서 실행하며 사진을 외부로 업로드하지 않습니다.

- `src/forest-move-in.ts` / `.css`: 입주 화면, 파일 선택·드롭, 5초 촬영, 오류·취소 처리.
- `src/forest-resident.worker.ts`: 로컬 이미지 분류, 형체 분할, HumanSeg·Pose 인식.
- `src/forest-resident-model.ts`: 이미지 윤곽 분석, 미니어처 메시와 부위별 텍스처.
- `src/forest-residents.ts`: 중앙 소개, 입주 이동, 구면 보행과 장애물 회피.

데스크톱 Chromium에서 실제 로컬 모델과 테스트 카메라 이미지를 사용해 동물형/윤곽형 생성, 부위별 매핑, 입주와 이동을 확인했습니다. 전체 플랫폼 최적화와 실물 카메라별 인식 품질 검증은 별도 작업입니다.

## 14 · 동물의 숲 확장판

13번의 기본 입주·산책 버전은 그대로 유지합니다. 14번은 별도의 맵과 주민 목록을 가지며, `/#animal-forest-extended`로 선택할 수 있습니다. 개발 서버는 사용자가 직접 실행합니다.

- **주민 클릭:** 캐릭터의 앞쪽에서 살짝 내려다보며 따라갑니다. 드래그로 캐릭터 주위를 둘러보고 휠로 거리를 조절합니다. 같은 주민을 다시 클릭하거나 `지구본으로`를 누르면 이전 지구본 시점으로 돌아갑니다.
- **길게 누르기:** 약 0.42초 누르면 주민이 들려 발버둥 칩니다. 드래그로 옮기고 놓으면 가까운 빈 땅에 내려놓습니다. 화면 가장자리에 잡고 있으면 지구본이 돌아가 반대편으로도 옮길 수 있습니다. 물·나무·다른 주민과 겹치는 위치는 가장 가까운 빈 땅으로 보정합니다. Esc 또는 포인터 취소는 원래 위치로 되돌립니다.
- **주민회의:** 나무·덤불·장식물을 비워 둔 공터로 주민들이 이동합니다. 서로 떨어진 자리를 배정하고, 나무를 우회하며 이미 도착한 주민이 길을 막으면 다시 경로를 찾습니다. 강을 건너야 하는 구간은 작은 점프로 이동합니다. 모인 뒤에는 서로를 바라보며 작은 몸짓을 유지합니다. `회의 마치기`를 누르면 다시 산책합니다.
- **미리보기 수정:** 14번은 자동 입주 대신 `수정하기`와 `이 모습으로 입주하기`를 표시합니다. `텍스처 밀기`로 표면을 드래그해 주변 UV를 부드럽게 늘이거나 줄입니다. 메시 정점은 변경하지 않습니다. 브러시 크기, 모델 돌리기, 되돌리기(최근 20회), 처음으로, 수정 완료를 제공합니다. 수정 내용은 입주 후에도 유지됩니다.

확장 동작은 `src/forest-residents-extended.ts`, 텍스처 편집은 `src/forest-texture-editor.ts`, 구면 경로와 브러시 계산은 `src/forest-extension-math.ts`, UI는 `src/forest-extended.css`에 있습니다. 기존 주민 생성·분할·텍스처 모델을 함께 사용합니다. 두 예제의 주민은 각각 별도로 IndexedDB에 저장됩니다.

개발/미리보기 서버를 띄우지 않고 계산 테스트 및 로컬 파일로 빌드한 Chromium 테스트 화면에서 편집·되돌리기, 추적/복귀, 집기/놓기, 실제 숲 지형의 주민 8명 집결과 회의 종료를 확인했습니다. 테스트 주민은 합성 사진·분석 입력을 사용했으며, 이번 변경에서는 카메라 인식과 전체 플랫폼 검증을 반복하지 않았습니다.


### 형체 마스크 보정 · 주민 저장 · 싱크홀

13·14번 공통으로 흰색·단색 배경 이미지는 이미지 가장자리에서 연결된 비슷한 배경색만 제거합니다. 검은 외곽선 안쪽의 흰 눈·치아·옷은 형체에 포함하고, 외부로 열린 팔·다리 사이 여백은 제거합니다. 최대 640px 해상도를 유지하여 얇은 팔다리와 외곽선을 보존하고, 축소된 외곽선의 1px 틈은 닫아 흰 내부가 배경으로 새는 것을 줄입니다. 복잡한 배경에서는 배경색과 형체 후보로 분할 시작점을 찾고 Magic Touch의 전경 확률 마스크를 사용합니다. 이 모델의 category 출력은 실제로 0/255를 사용하므로, 1을 전경으로 가정하던 처리를 제거했습니다. 이미지 테두리를 감싸는 배경 마스크는 반전을 바로잡고, 작은 잡음을 제거하며 분리된 귀·팔다리 같은 유의미한 조각은 유지합니다. 투명 PNG의 알파는 임의로 뒤집지 않습니다. 빈 마스크나 사각 프레임만 남은 결과는 모델 생성 전에 거절하고 이미지 재선택을 안내합니다. 투명 이미지·모델 분할 결과의 실제 구멍은 보존합니다.

완성한 주민의 메시·사람 영역 텍스처·수정된 UV·위치·방향은 `interactive-web-forest-residents` IndexedDB에 저장됩니다. 입주 즉시 모델을 저장하고, 이동 상태는 주기적으로 및 수동 배치·예제 전환 시 저장합니다. 저장된 모델을 직접 복원하므로 다시 입주하거나 카메라를 켤 필요가 없습니다. 원본 카메라 사진과 업로드 이미지는 저장하지 않습니다. 13번과 14번의 주민 목록은 독립적입니다. 저장 범위는 **같은 브라우저 프로필과 같은 사이트 주소(origin: 프로토콜·호스트·포트)**이며, 브라우저의 사이트 데이터 삭제는 저장된 주민도 지웁니다. 저장 실패 시 화면의 저장 상태에서 재시도할 수 있습니다.

14번에서 주민을 길게 잡으면 보이는 땅에 싱크홀이 열립니다. 일반 땅에 놓으면 이동하고 싱크홀이 닫힙니다. 싱크홀 위에서는 `놓으면 이 주민이 영구 방출됩니다`가 표시됩니다. 놓으면 IndexedDB 삭제를 먼저 완료한 뒤 주민이 구멍으로 줄어들며 떨어지고 땅이 자연스럽게 닫힙니다. 삭제가 실패하면 주민은 원래 땅으로 돌아옵니다. 삭제한 주민의 모델·이미지 데이터는 남기지 않으며, ID 삭제 기록으로 오래된 탭의 자동 저장이 주민을 되살리지 못하게 합니다. 다른 열린 탭에도 방출을 알립니다. Esc·포인터 취소는 방출하지 않습니다.

- `src/forest-subject-mask.ts`: 단색 배경의 외부 연결 영역 제거, 전경/배경 방향 판별, 연결 영역 정리, 분할 시작점 추천.
- `src/forest-resident-storage.ts`: 모델/UV 직렬화, IndexedDB 저장과 복원, 영구 삭제.
- `src/forest-sinkhole.ts`: 싱크홀 형태·등장/종료·드롭 영역, 지형 셰이더 연동.

서버 없이 계산 테스트 및 로컬 HTML 테스트 화면으로 마스크 반전, 브라우저 종료 후 모델·수정 UV 복원, 정상 드롭, 싱크홀 방출, 다른 탭 반영, 오래된 저장 시도 후 삭제 유지, 삭제 실패 시 복귀를 확인했습니다. 테스트 저장소는 별도의 임시 브라우저 프로필을 사용했습니다.

단색 배경 수정은 30개 계산 테스트와 서버 없는 로컬 Chromium 화면에서 검증했습니다. 사용자가 제공한 스폰지 캐릭터 원본과 테스트용 사람 사진을 실제 MediaPipe 작업자에 입력하여 외곽 마스크·흰 눈/셔츠/소매·얇은 팔/다리·다리 사이 배경을 확인하고 3D 모델을 생성했습니다. 복잡한 배경의 고양이 사진으로 단색 분리 대신 전경 확률 마스크를 사용하는 경로도 확인했습니다.

### 사람형 주민의 얼굴과 의상

새로 생성되는 사람형 주민은 업로드한 형체 이미지에서 얼굴(코·양쪽 눈)과 양쪽 어깨가 충분히 확인될 때만 선택합니다. 카메라에 사람이 있다는 이유나 어깨만 검출된 불확실한 결과로 사람형을 선택하지 않습니다. 사람형의 카메라 텍스처는 얼굴 하나만 만들고 머리 앞면에 사용합니다. 머리 옆·뒤와 귀·손은 얼굴에서 추출한 단색 피부색이며, 몸통·소매·바지·신발에는 사진을 사용하지 않습니다. 카메라 얼굴 랜드마크가 없으면 임의의 몸통 크롭을 얼굴에 붙이지 않고 재촬영을 안내합니다.

`src/forest-resident-outfit.ts`에서 6가지 조화로운 팔레트와 줄무늬·가디건·체크·포켓 디자인 중 의상을 무작위로 생성합니다. 직물 결, 소매/밑단, 단추나 주머니, 바지와 신발을 함께 구성합니다. 완성된 텍스처와 디자인은 주민 모델에 저장되어 다시 접속해도 동일하게 복원됩니다. 13·14번의 신규 사람형 주민에 적용하며, 기존에 저장한 주민은 저장 당시 외형을 유지합니다.

서버 없이 로컬 Chromium에서 사람/윤곽/동물 분기, 머리에만 사진 텍스처가 있는지, 카메라 사진을 바꿔도 의상 텍스처가 영향을 받지 않는지, 저장·복원 후 의상과 얼굴 재질이 동일한지 확인했습니다. 실제 MediaPipe 모델과 테스트용 사람 사진으로도 사람형·얼굴 전용 텍스처 생성까지 확인했습니다. 기존 계산 테스트 30개와 프로덕션 빌드도 통과했습니다.

### 주민 이름과 추적 시점 대화

13·14번의 입주 화면에 주민 이름 입력란(최대 20자)이 있습니다. 비워 두면 사용하지 않는 `주민 1`, `주민 2` 등의 이름을 자동으로 붙입니다. 이름은 주민 상태와 함께 IndexedDB에 저장합니다. 이름이 없던 기존 주민은 불러오는 트랜잭션에서 자동 이름을 배정하고 저장하므로, 다시 접속하거나 다른 탭에서 불러와도 이름이 유지됩니다. 기존 사용자 지정 이름과 방출 기록은 보존합니다.

14번에서 주민을 클릭해 추적 시점에 들어가면 화면 아래에 크림색 곡선 말풍선, 민트색 이름표, 노란 진행 표시가 나타납니다. `src/forest-dialogue-lines.ts`에 작성한 서로 다른 한국어 대사 100개를 주민마다 섞어 사용합니다. 한 바퀴를 다 읽기 전에는 같은 주민의 대사가 반복되지 않습니다. 한 글자씩 표시하고 문장부호에서는 잠깐 쉬며, 읽을 시간을 둔 뒤 다음 대사로 넘어갑니다. 말풍선을 누르면 타이핑 중인 문장을 완성하고, 다시 누르면 다음 이야기를 듣습니다. 지구본 시점 복귀·집기·입주 화면 열기·예제 전환 시에는 대화를 숨깁니다.

대화 UI는 `src/forest-dialogue.ts`와 `src/forest-dialogue.css`, 이름 처리는 `src/forest-resident-names.ts`에 있습니다. 대사 수·중복·무작위 순환·이름 보존을 포함한 계산 테스트 34개와 빌드를 통과했습니다. 서버 없는 로컬 Chromium 숲 화면에서 실제 주민 클릭, 점진적 타이핑, 수동/자동 다음 대사, 재클릭 복귀, 기존 무명 주민 이름 배정, 브라우저 재시작 및 새로고침 후 이름 유지를 확인했습니다.

### 마네킹 이미지 생성 중 인식 엔진 중단 수정

세로형 마네킹 AVIF 원본으로 `Aborted(). Build with -sASSERTIONS for more info.` 오류를 재현했습니다. 실패 지점은 업로드 이미지의 Pose Landmarker 분석이며, 추가 분할 마스크를 출력하는 경로에서 `image_frame.cc:415: 1 == ChannelSize() (1 vs. 4)` 검사가 실패했습니다. 업로드 이미지에는 관절 정보만 필요하므로 해당 단계의 `outputSegmentationMasks`를 끕니다. 촬영 사진에는 기존 HumanSeg·Pose 마스크 교차를 유지하며, 같은 작업자를 재사용할 때 촬영 사진 분석 전에 마스크 출력을 다시 켭니다. 결과 마스크는 예외가 발생해도 해제하고, 런타임 중단 시 개발용 빌드 문구 대신 중단 단계와 재촬영 안내를 표시합니다.

실제 로컬 MediaPipe 모델로 같은 마네킹을 두 번 연속 분석하여 사람형, 얼굴 전용 사진 텍스처, 랜덤 의상까지 생성되는 것을 확인했습니다. 서버를 열지 않는 회귀 확인은 `node tests/forest-person-vision.check.mjs <사람형_참고이미지_경로> <촬영용_사람사진_경로>`로 실행할 수 있습니다. 입력 이미지는 저장소에 포함하지 않습니다.

## 방명록 · Supabase 연결

메인 화면 우상단의 **방명록 ↗** 버튼이 `guestbook.html`로 이동합니다. 이름(30자)과 내용(500자)을 작성하면 Supabase에 저장된 결과를 즉시 포스트잇으로 붙입니다. 다른 방문자의 새 글은 Supabase Realtime으로 받고, 연결 중 누락된 글을 보완하기 위해 30초마다 최신 목록도 조회합니다. 처음에는 최신 30개를 표시하며 **이전 방명록 더 보기**로 추가 조회합니다.

기존 15개 인터랙션은 `src/main.ts`에 유지됩니다. 방명록은 별도 진입점 `src/guestbook/main.ts`로 빌드되어 카메라·3D 예제 코드를 불러오지 않습니다. GitHub Pages의 `/Interactive-Web_6/` 하위 경로를 그대로 사용하고, 별도의 애플리케이션 서버나 로그인은 필요하지 않습니다.

### 1. Supabase 테이블·권한·실시간 알림 설정

1. [Supabase Dashboard](https://supabase.com/dashboard)에서 생성해 둔 프로젝트를 엽니다.
2. **SQL Editor → New query**를 엽니다.
3. 이 저장소의 [`supabase/guestbook.sql`](supabase/guestbook.sql)을 열어 **전체 내용**을 복사합니다.
4. SQL Editor에 붙여넣고 **Run**을 누릅니다. 성공 메시지가 표시되어야 합니다.
5. **Table Editor**에서 `public.guestbook_entries`가 생겼는지 확인합니다. 열은 `id`, `name`, `message`, `created_at`입니다.
6. **Database → Publications → supabase_realtime**에서 `guestbook_entries`가 포함되어 있는지 확인합니다. 위 SQL이 이미 등록하므로 보통 별도 토글 설정은 필요하지 않습니다.

SQL은 RLS를 켜고 방문자에게 조회·추가만 허용합니다. 이름과 내용의 길이도 데이터베이스에서 검사하고, 작성 시각은 데이터베이스가 생성합니다. 방문자에게 수정·삭제 권한은 없습니다. 동일 SQL을 다시 실행해도 기존 글은 삭제되지 않습니다. 단, 같은 이름으로 다른 구조의 테이블을 미리 만든 경우에는 자동 변환하지 않으므로 오류 내용을 먼저 확인하세요.

### 2. 프로젝트 URL과 공개 키 확인

1. Supabase 프로젝트의 **Connect** 창에서 **Project URL**을 복사합니다. 찾기 어려우면 **Project Settings → Data API**에서도 확인할 수 있습니다. 형식은 `https://프로젝트참조값.supabase.co`입니다. PostgreSQL 연결 문자열을 사용하지 않습니다.
2. **Project Settings → API Keys**에서 `sb_publishable_...`로 시작하는 **Publishable key**를 복사합니다.
3. 구형 프로젝트의 `anon` 공개 키도 같은 환경변수에 넣어 사용할 수 있습니다.

브라우저에서 쓰는 공개 키는 배포된 코드에 포함됩니다. 데이터 접근 제한은 1단계의 RLS·테이블 권한이 담당합니다. **Secret key(`sb_secret_...`), `service_role` 키, 데이터베이스 비밀번호는 넣지 마세요.** 이 기능은 Supabase Auth 로그인을 사용하지 않으므로 Auth의 Site URL이나 Redirect URL을 등록할 필요가 없습니다. 공개 키와 비공개 키의 차이는 [Supabase API keys 문서](https://supabase.com/docs/guides/getting-started/api-keys)를 참고하세요.

### 3. GitHub Pages 배포용 변수 등록

로컬 `.env.local`은 GitHub에 올라가지 않으므로 **배포용 값은 GitHub에도 따로 등록**해야 합니다.

1. GitHub의 이 저장소에서 **Settings → Secrets and variables → Actions → Variables**를 엽니다.
2. **New repository variable**을 눌러 아래 두 개를 정확한 이름으로 만듭니다. **Secrets 탭이 아닌 Variables 탭**입니다. 값에 따옴표를 붙이지 마세요.

   | Name | Value |
   | --- | --- |
   | `VITE_SUPABASE_URL` | 2단계의 Project URL |
   | `VITE_SUPABASE_PUBLISHABLE_KEY` | 2단계의 Publishable key 또는 legacy anon 키 |

3. **Settings → Pages → Build and deployment → Source**가 **GitHub Actions**인지 확인합니다.
4. 이번 변경 파일을 커밋하고 `main` 브랜치로 푸시합니다. 코드 변경과 배포 변수는 이 작업에서 자동으로 원격 저장소에 반영하지 않았습니다.
5. **Actions → Deploy to GitHub Pages**에서 `build`와 `deploy` 작업이 모두 성공했는지 확인합니다.
6. 이미 코드가 올라간 뒤 변수를 등록했다면 **Actions → Deploy to GitHub Pages → Run workflow → main → Run workflow**로 다시 빌드·배포합니다. 환경변수 변경은 기존 배포에 즉시 적용되지 않습니다.
7. 배포된 [방명록 페이지](https://youngsun-onearth.github.io/Interactive-Web_6/guestbook.html)를 엽니다.

`.github/workflows/deploy.yml`이 위 Variables를 빌드에 전달하도록 구성되어 있습니다. 설정이 비어 있거나 잘못된 키 종류이면 방명록은 준비 중 안내를 표시하고 작성 폼을 비활성화합니다. 기존 메인 페이지는 계속 이용할 수 있습니다.

### 4. 로컬에서 확인하려면 (선택)

1. 프로젝트 루트에서 `.env.example`을 복사해 `.env.local` 파일을 만듭니다.
2. 아래 값에 실제 Project URL과 공개 키를 넣습니다.

   ```dotenv
   VITE_SUPABASE_URL=https://프로젝트참조값.supabase.co
   VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_실제공개키
   ```

3. 터미널에서 `npm install`을 실행합니다.
4. 사용자가 직접 `npm run dev`를 실행하고 터미널에 표시된 주소에서 방명록 버튼을 누릅니다. 이미 개발 서버가 켜져 있었다면 환경변수를 읽도록 재시작합니다.
5. 서버 없이 코드만 확인하려면 `npm run build`와 `npm test`를 실행합니다. 기존 `npm run test:e2e`는 서버 자동 실행 설정이 있으므로 이 절차에는 사용하지 않습니다.

`.env.local`은 Git 추적에서 제외됩니다. 여기에 넣은 공개 키 역시 브라우저용 빌드에는 포함됩니다.

### 5. 실제 연결 확인 순서

1. 메인 페이지 우상단 **방명록** 버튼으로 이동합니다.
2. 이름과 내용을 적고 **작성하기**를 누릅니다. 저장 완료 안내와 새 포스트잇이 나타나는지 확인합니다.
3. 페이지를 새로고침해도 글이 남아 있는지 확인합니다.
4. Supabase **Table Editor → guestbook_entries**에서도 같은 글을 확인합니다.
5. 같은 방명록을 다른 브라우저나 휴대폰에서도 열어 둡니다. 한쪽에서 작성하면 다른 쪽에도 새로고침 없이 포스트잇이 나타나야 합니다.
6. `guestbook.html` 주소를 직접 열거나 새로고침해도 정상 표시되는지 확인합니다.

실제 Supabase URL·공개 키가 제공되지 않은 상태에서는 원격 저장·실시간 전달 확인을 완료할 수 없습니다. 위 확인은 SQL 실행과 환경변수 등록 후 수행하세요.

### 문제 해결과 관리

| 증상 | 확인할 내용 |
| --- | --- |
| “방명록을 준비하고 있어요” | GitHub **Variables**의 변수 이름·값을 확인하고 다시 배포합니다. 로컬은 `.env.local` 저장 후 개발 서버를 재시작합니다. |
| 목록 조회 또는 저장 실패 | Supabase 프로젝트가 활성 상태인지, URL과 키가 같은 프로젝트인지, SQL 전체가 성공했는지 확인합니다. 브라우저 개발자 도구 Network의 `guestbook_entries` 요청 응답도 확인합니다. |
| `401` / invalid API key | 공개 키와 URL을 다시 복사합니다. 키를 교체했다면 다시 빌드·배포합니다. |
| `403` / `42501` | RLS 정책과 `SELECT`/`INSERT` 권한을 확인합니다. 제공한 SQL을 다시 실행할 수 있습니다. |
| 테이블 없음 / `PGRST205` | 같은 Supabase 프로젝트에서 SQL을 실행했는지, 테이블 이름이 `guestbook_entries`인지 확인합니다. |
| 내 글은 보이지만 다른 기기에 즉시 나타나지 않음 | `supabase_realtime` publication에 테이블이 포함되어 있는지와 WebSocket 연결을 확인합니다. 30초 후에만 보이면 Realtime 설정을 점검하세요. |
| Pages에서 404 | 이번 `vite.config.ts`와 `guestbook.html`이 함께 배포되었는지, Actions 배포가 성공했는지 확인합니다. |

불필요한 글은 프로젝트 관리자가 Supabase **Table Editor**에서 삭제할 수 있습니다. 이미 열려 있는 화면에서는 페이지를 다시 열어 삭제 결과를 확인합니다. 현재 구현은 누구나 읽고 작성하는 공개 방명록이며, 이름은 본인 인증을 거치지 않습니다. RLS는 타인의 글 수정·삭제를 막지만 자동 도배를 제한하는 장치는 아닙니다. CAPTCHA·서버 측 작성 제한·승인 대기 기능은 이번 범위에 포함하지 않았습니다.
